# 每轮上下文选择与遗漏恢复

2026-10-23 补充设计。回应的重点：不追求一次性找出完美、固定的最小集合；根据执行过程持续更新每个角色下一次调用需要的工作集。本次仍只修改设计文档。

## 1. 把目标改成“当前这一步足够，而且可以纠错”

这里的“每轮”指每次模型调用，不仅是用户发送一条消息后的整轮任务。搜索、读取原文、处理冲突、写报告需要的上下文不同。

控制上下文改变的是模型输入和取用材料的方式，不是直接修改模型的 attention 算法；节省 token 也不保证自动转化成更强推理。目标是减少无关干扰，同时保留完成当前动作所需的信息，并实测质量、总成本和延迟。

对于开放研究，通常不能在执行前证明某个集合是全局最小且充分。可以采用明确、可检查的近似：必要约束不丢失；当前步骤有足够材料或有明确补查动作；完成结论有可核验证据；离线删除实验没有发现明显可省去的材料。

上一版文档中的 token 上限是容量约束，不是充分性的证明。关于“相关”和“足够”的区别，可参考 [Sufficient Context](https://arxiv.org/abs/2411.06037)；该研究讨论回答所需信息是否齐全，并不替本项目解决动态 agent 的最优选择问题。

## 2. 每次调用前先构造一张需求卡

`StepDemand` 由程序状态和模型上一轮的可见输出共同生成：

```text
role / task_id / phase
objective_ref + active_requirement_ids
current_action                 # 搜索、读源码、核验、比较、写作等
latest_observation_refs         # 上一轮真正返回了什么
missing_information[]           # 下一步缺什么，不能只写“需要更多资料”
unresolved_conflicts[]
mandatory_constraints[]         # 版本、日期、范围、输出要求等
expected_output                 # 本次是查询、判断、任务卡还是报告段落
remaining_budget
```

初始需求由用户任务和角色决定；之后使用实际事件更新，不能只沿用主脑最初的计划。任务换版本、工具失败、出现反证或用户修改目标时，重新生成需求。

不需要每轮额外调用一个 LLM 来“先计划如何选上下文”。常见情况从 task ledger、当前阶段、未解决问题和已完成工具调用即可得到需求。可让执行者在正常输出中附短的 `next_intent` 和 `missing_information`，但它们只是建议，程序检查是否仍符合用户目标；不能因为它执着某个错误方向，就过滤掉反证。

若下一步不确定，先保留任务定义、最近完整交互和较宽的相关材料索引，允许执行者选择下一动作。不要用猜测的下一步强行缩窄输入。

## 3. 真正决定“塞什么”的选择顺序

先按身份、角色、任务和版本过滤候选，再按下表选择。优先级是本项目设计起点，不是固定的数学最优解。

| 顺序 | 内容 | 纳入理由 |
| --- | --- | --- |
| 0：不可省 | 用户硬约束、当前目标、角色边界、适用的工具协议 | 缺失后可能做错任务或越界；不得让相关性评分压掉 |
| 1：当前动作必需 | 待核验主张、当前源码/数据、最新工具结果中决定下一步的部分 | 对这一步具有直接用途 |
| 2：解释它所需的依赖 | 定义、版本、前置步骤、例外、否定条件、相邻原文 | 独立片段容易误读，必须作为依赖一起选 |
| 3：未解决的反证和缺口 | 与本任务有关的冲突证据、仍未满足的要求 | 防止选择器只留下支持现有判断的材料 |
| 4：必要操作知识 | 当前启用工具的说明、当前需要的 Skill 步骤 | 让本次操作可执行；仅有任务关键词相似不足以触发加载 |
| 5：辅助背景 | 有效 memory、已完成子任务的短结果、额外独立来源 | 在覆盖不足或有增益时纳入，避免重复 |

材料可以在不同轮次改变优先级。“昨天不需要”不意味着“以后没用”；“最近出现”也不意味着“这轮必需”。

对每条候选材料记录：`supports_requirement_ids`、`required_for_action`、`depends_on`、`contradicts`、`source_version`、`valid_scope`、`token_cost`。这些关系可能由规则、代码结构或模型建议得到，模型提取的关系标为待验证，不能把它们当作完美知识图谱。

选择时先补没有覆盖的需求，再考虑独立佐证，最后删除重复载荷。不要只做相似度 Top-K：十条介绍性资料可能都“很相关”，却缺少一条决定答案的限制条件。检索排序只能在已有候选中挑选，遗漏候选时还需要扩展检索。

MVP 不需要训练复杂打分模型。用必留字段、阶段规则、元数据检索、去重和简单 reranker 即可；语义难判断时才调用上下文管理角色。

## 4. Skill、Memory 与证据不能采用同一种注入规则

| 内容 | 默认策略 | 重新加载条件 |
| --- | --- | --- |
| 硬约束 / 权限规则 | 保留适用部分，由受信任配置控制 | 用户或管理员正式修改 |
| Skill | 先检索获准的名称、适用条件、步骤摘要；当前动作需要时加载详细步骤 | 阶段切换、调用新能力、执行失败需要查手册 |
| Memory | 按当前实体/项目/时间/任务类型检索，携带来源与适用范围 | 新任务需求命中、旧事实与新证据冲突 |
| 原始证据 | 当前核心片段进窗口，全文外存；数字、否定、例外、日期尽量保留原文 | 需要精确引用、出现矛盾、摘要不够支持判断 |
| 工作历史 | 保存当前进度、失败方向、未解决问题与最近完整交互 | 重复失败、需要恢复上一动作、查明决策依据 |

被检索到的外部文字不自动成为规则。Memory 里的旧偏好不能覆盖本次用户指令，Skill 文本不能授予新工具权限。本文提出的是本项目运行时的 memory 管理，不修改编码助手的主机记忆。

索引也需要控制大小：按权限和任务检索少量候选卡片，不把所有历史材料的目录一股脑放进 prompt。

## 5. 要有一个上下文管理角色，但日常机制由程序执行

保留原 `ContextBuilder`，增加逻辑上的 `ContextManager`，分成两部分：

| 部分 | 负责 | 不负责 |
| --- | --- | --- |
| 确定性上下文服务 | 身份/权限、预算、版本、存档、选择规则、工具配对、依赖记录、恢复调用 | 判断一个复杂论证是否已经充分 |
| 按需语义顾问 | 根据 StepDemand 和有限候选建议取舍，指出缺口、依赖与歧义 | 任意扩权、删除原文、替主管改目标、给最终报告自行盖章 |

语义顾问在阶段切换且选择不清、证据冲突、回读仍不充分或必要材料超预算时介入。平常每轮通过程序规则更新工作集即可。它使用独立短调用，作用域绑定到当前 run/agent；不维护一个包含所有角色私有历史的共享聊天窗口。

顾问输出 `SelectionProposal`：

```text
include_refs[] + reason_codes[]
offload_refs[] + recoverable_refs[]
required_dependencies[]
uncovered_requirements[]
uncertain_selections[]
```

程序校验提议能否执行。没有任何内容可以因为管理角色说“没用”就直接从档案删除。Manager 失效时，回退到规则选择、最近有效工作状态和必要原文；预算不够则明确停止或拆任务。

主管决定做什么，Manager 决定本轮给什么材料，Reviewer 检查结论和需求覆盖。Reviewer 可以直接请求获准原文，不必让同一个语义选择器再次批准，从而降低共同盲点。

这个角色是否值得额外调用，要通过实验决定；不假定多加一个模型一定更省钱。

## 6. “充分”怎样在运行中检查

每个当前需求记录 `covered / missing / uncertain`，并附 evidence ref 或明确的下一步工具动作。程序检查字段/版本/引用完整性；必要时 Reviewer 判断语义上是否足以支持决定。

区分两类充分性：

- **行动充分**：现在足够决定下一次搜索或读取。例如发现没有错误恢复证据，已经足够发起针对性检索，不必等到整个问题全部回答才能行动。
- **结论充分**：现在足够支持准备输出的事实和限定条件。关键依据缺失时不能靠“模型觉得有把握”直接通过。

不能用“成功生成一段答案”证明充分。模型可能靠已有知识碰巧答对，也可能自信地补出来源没有提供的细节。事实研究还要检查来源真实性、适用版本和证据质量，而不仅检查文字上能拼出一个答案。

离线在固定任务集做删除/替换实验：移出一个材料组，比较需求覆盖、事实支持和调用成本；恢复后再检验。组是依赖闭包，例如定义+公式、条件+例外，避免只对孤立句子做实验。加入删掉关键反证的负对照，确认评测确实会识别质量下降。

这种实验用于调整选择策略，不在每一轮线上穷举。即使当前材料逐组删除都会变差，也只得到当前候选和评测条件下的局部结果，不能声称找到了全局最小集合。

## 7. 被移出的材料怎样找回来

采用“保留档案、移出工作集”。每次移出记录：`artifact_id`、原始版本/hash、适用范围、移出原因、相关需求、恢复入口、触发回读条件。先确认原文持久化成功，再缩减工作集；保存失败就保留必要内容或中止本轮压缩。

新增受控工具：

```text
request_context(need, purpose, known_refs?, expected_detail?)
```

执行者可以只说需要什么，不必知道丢失材料的文件名。例如：“需要核验 v2.1 的索引一致性例外，确认刚才的断点恢复结论是否仍成立。”

运行时按当前身份查找获准索引：精确 ref/版本 → 关键词与元数据 → 语义召回和相邻段落 → 必要的原文。一次不够时允许有上限地扩展范围；不能只在先前生成的摘要里搜索，否则摘要漏掉的内容永远回不来。

返回 `ContextPatch`：`restored_refs`、`exact_excerpts`、`source_versions`、`affected_requirements`、`still_missing`、`status`。状态至少区分 found / partial / unavailable / access_denied；找不到不等于不存在。

回读仍受权限约束。若所需发现来自另一个研究员，走已发布结果与授权流程；不能以恢复为理由读取它的全部私有日志。确需新授权时由宿主策略决定，Manager 不能自授。

### 谁发现遗漏

| 信号来源 | 触发信号 |
| --- | --- |
| 执行者 | 缺定义、无法引用、无法执行、发现自相矛盾、工具前置条件缺失 |
| 程序 | 需求项未覆盖、引用失效、版本变化、连续重复查询、工具缺少参数 |
| Reviewer | 结论缺支持、限定语丢失、证据与主张冲突 |
| 定点复核 | 最终交付前，按关键需求独立检索例外/反证，抽查被移出的关联材料 |

执行者可能不知道自己遗漏了什么，因此不能只依靠它主动请求。最终关口需对关键需求做一次范围受控的独立复核，必要时从原始档案检索，不重复使用完全相同的候选清单。仍然无法保证发现所有未知遗漏，实验要测漏检率。

## 8. 找回内容后，已经产生的错误结论怎么办

恢复材料只是第一步。增加有上限的修复流程：

```mermaid
flowchart LR
    A[发现信息缺口] --> B[按权限检索原始档案]
    B --> C[恢复准确片段与版本]
    C --> D[标记可能受影响的结论]
    D --> E[补充核验或重算相关任务]
    E --> F[更新下游摘要与报告]
    F --> G[重新审查并记录新版本]
```

记录 `claim → evidence → result → report_section` 的派生关系，以及哪个 request 使用了哪个版本。新证据可能从未参与旧结论，因此**仅追踪既有依赖边不够**：还要按需求、实体、版本和时间范围找出可能受影响的主张。

受影响对象先标 `needs_revalidation`，暂停把它们继续当已确认事实分发。核验后保留成立结论，修正或撤销不成立结论，并使下游依赖和旧 review pass 失效；保留旧版本以便审计。

如果原 agent 已被错误前提带偏，可开启新的短 invocation，只带任务、恢复的原文、仍有效发现和明确的撤销说明，不重放整段失败历史。普通补充缺口可以继续原 invocation。两者都沿用总预算和修复计数，不通过重启“洗掉”成本和失败记录。

对既已交付的报告，在产品内保存 correction/version 关系并清楚呈现变化；外部自动通知属于另行配置的产品行为，本设计不默认授权 agent 给其他人发送消息。

MVP 无需图数据库：JSON 关系表与宿主维护的反向索引即可。无法准确定位影响范围时，扩大到对应子任务/章节重审；不能假装定位精确而放过相关结论。

## 9. 用本项目研究任务举一个逐轮例子

以下为虚构研究场景，用于解释选择逻辑，不声称真实框架具有这些行为。

任务：“判断框架 v2.1 导入中断后，能否安全恢复且不产生重复记录。”

| 调用阶段 | 本轮放入 | 暂时移出 | 更新原因 |
| --- | --- | --- | --- |
| 拆问题 | 版本约束、成功标准、可用源码/文档索引 | 全文、写报告 Skill | 先明确需要核验断点、幂等和一致性 |
| 查导入入口 | 入口函数、任务卡、代码读取说明 | 已完成的检索日志 | 当前需要确定调用链 |
| 核验重试 | 重试与写入函数、ID 生成逻辑、相关测试 | 入口的无关参数说明 | 新调用关系揭示了必要依赖 |
| 出现疑点 | 上述内容加恢复的“部分索引提交失败”例外原文 | 已被证实无关的介绍段落 | 例外可能推翻“可以安全恢复”的初步判断 |
| 写报告 | 核验后的结论、限制条件、引用、输出格式 | 搜索过程和工具操作手册 | 下一步是解释结论，不再执行搜索 |

若例外最初被移出，Reviewer 发现“没有核验跨索引一致性”，触发 request_context；恢复例外后将相关初步结论置为待重审，再更新报告。无需恢复所有角色的完整历史。

## 10. 最小实现与新增验收

新增或扩展对象：`StepDemand`、`SelectionProposal`、`ContextPatch`、`EvictionRecord`、`RevalidationEvent`。文件落点优先扩展已有设计中的 `context.py / artifacts.py / reviewer.py`，不增加多层服务。

每轮步骤：更新事实状态 → 构造 StepDemand → 权限过滤与候选检索 → 必需内容和依赖优先 → 预算内组装 → 调用 → 归档结果并更新下一轮需求。语义 Manager 是按需支路。

在原 A/B/C/D 实验里，将动态选择作为 B/D 的明确版本；需要比较 Manager 时，在相同动态规则基础上另设“语义顾问关闭/按需开启”，避免把动态规则收益归给新增角色。

新增测试：相同任务执行到不同阶段应选择不同内容；新证据出现后会重排；关键例外被故意移出后能恢复；执行者未主动求助时 Reviewer 能发现部分遗漏；新反证能使旧报告审批失效；存档失败时不做不可恢复裁剪；Manager 超时有回退；恢复次数到限能明确停止。

新增指标：关键材料漏选率、首次恢复成功率、无效回读率、遗漏发现延迟、受影响结论修复率、审查漏检/误报、Manager 成本、恢复总成本和端到端完成率。已知必要材料由标注任务提供；开放研究只能估计，不能把自动选择器自报的覆盖率当真值。

参考方法与区别见 [SOURCES.md](SOURCES.md) 的 S12–S17。本方案不要求完美上下文分类器，也不要求自动跨 run 学习；先把每轮需求、取舍理由和恢复链路做得可检查。
